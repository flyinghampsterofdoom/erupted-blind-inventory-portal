# Purchasing V3 — historical PDF preservation resolution

2026-10-18. Original investigation and revised plan. **Do not deploy.**

The later [approved local correction](purchasing-v3-pdf-preservation-correction.md) supersedes the disk-only proposal and the pre-correction resolver findings below. This document preserves the investigation record; it does not describe the current local implementation.

**Finding:** No original was recovered from the accessible locations examined. All 50 historical database references remain unchanged. This does not establish permanent loss: vendor-held copies, email attachments, offline backups and provider-only recovery outside available access remain possible. No historical document was regenerated or relabeled as an original.

**Safety conclusion:** The revised plan below is suitable for owner review, but the currently approved revision is not yet safe to deploy under the revised document-preservation requirements. It still writes new PDFs to ephemeral storage and regenerates missing documents during GET downloads. A bounded preservation guard and durable storage configuration must be implemented/verified before a newly reviewed release is deployed. No application code or production configuration was changed in this investigation.

## Revised preservation and deployment plan

1. **Preserve the historical gap explicitly.** Retain all 50 `pdf_path` values and original PO records exactly. Keep the missing-file manifest with the release/backup evidence. Record database backup verification separately from file backup verification. If a copy later appears, verify provenance before treating it as an original; a reconstruction must never be called an original. Do not regenerate historical POs in this work.
2. **Add only the necessary preservation boundary.** Before rollout, make downloads of missing historical artifacts return an explicit unavailable-original result without rendering, updating a path or committing a replacement. Test all 50 manifest references in isolated fixtures. Retain authorization and existing deliberate new-order PDF generation/PO editing behavior; use the existing error presentation. This guard is proposed, not implemented here. It changes the approved source and therefore requires an exact new reviewed revision; do not silently deploy it as `84747d0b…`.
3. **Use a durable disk at the existing PDF path.** Proposed target: a Render persistent disk mounted exactly at `/opt/render/project/src/generated/purchase_orders` on the existing single-instance web service. This lets the current writer and relative references use durable storage without a new accounting table, document ledger, storage-provider abstraction, purchasing engine or payment workflow. Do not repurpose the signage bucket. No disk was created or attached. Adding a Render disk triggers a deploy, so it must occur only in the later authorized maintenance/cutover sequence.
4. **Fail closed on an absent mount.** Verify the actual mount at web runtime, not merely directory existence, before accepting new PDF generation; no fallback to the checkout filesystem. An empty directory is not proof of durability. Disk access checks belong at runtime: Render build/pre-deploy jobs and cron do not share the web disk. Preserve write failures as visible errors rather than committing a reference to an unavailable artifact. Implement/verify this narrow guard with the storage correction.
5. **Back up files independently.** Inventory existing files and record path/size/SHA-256 in a backup manifest. Archive from the running web service's mounted directory and securely retain an independent copy; database exports alone do not cover it. Verify restore into a separate directory/volume and compare every hash before accepting the backup. Keep platform disk snapshots as an additional recovery layer, not the only copy. Render's daily snapshots imply up to a day of recovery exposure; the owner must approve the backup frequency/retention, with an immediate verified backup of the first authorized new PDF. No new backup automation was activated.
6. **Keep all approved migration/financial safeguards.** Refresh the verified production DB backup at the eventual maintenance window. Retain the forward 0037→0038 graph, identical existing migrations, coordinated web/cron SHA and schema checks, owner principal 6, Chase Visa account 2, Card 2 absent/recording blocked, unresolved SKU/cost warnings, no fabricated valuation, and the sole actual-card balance authority. No historical backfill or new financial writer is needed for this storage correction.
7. **Rehearse and smoke without historical mutation.** Rerun PO/PDF/receiving/payment regressions for the bounded new revision. Before activation, verify the actual durable mount, read-only authentication/navigation, preserved 50-reference manifest, and the missing-original response. Do not exercise the current regenerating GET behavior as a smoke test. No real PO/payment/receiving/Square mutations. Actual new-order/PDF generation remains a later separately authorized operation; the isolated checks below do not substitute for hosted mount validation.
8. **Retain safe recovery.** Do not detach/delete the disk during an application rollback. Retain 0038 evidence and Phase 1 authority after new business writes, with the reviewed feature quarantine. Restore file archives/snapshots in isolation first; restoring an older whole disk over newer PDFs would lose later files. Keep the original deployment recovery rules and never roll back the database across legitimate newer transactions.
