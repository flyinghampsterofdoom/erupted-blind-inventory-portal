Root cause and intent
The October 29, 2026 commit 9c3e93a7d9fd3f5c297f23227855a5be5fb0344e introduced the named-database OwnerInspectionTarget and explicitly kept reserved purchasing capabilities paused. The earlier Phase 9 integration was qualified only on disposable databases and simulated providers. Its production activation procedure was a proposal, with separately reviewed migrations and independent capability activation.
This was a staged-rollout safeguard, not a general rule that an authenticated owner may never purchase. It has persisted in production. The deployment blocker evidence verified owner-inspection mode enabled, public schema 20261107_0056, private worksheet schema p4_0003, and no Phase 5 PO ownership registry.

Four boundaries enforce that state: app.main selects the inspection target; integration_app accepts only inspection/calculation capabilities on that target; /api/context forces submission/authorization false; and worksheet-only composition omits the authorization application. A middleware also denies reserved mutations. The existing administrator session alone cannot make absent routes, tables, or grants available.

Existing operations and the compatibility decision
Manual worksheets, approved owner configuration/calculation, read-only Square inventory refresh, and the separately enabled existing-PO receiving worksheet depend on the current composition. The isolated Phase 5 migration would introduce a V4 PO ownership registry whose guards reject canonical legacy receiving. Simply mounting the isolated application or switching every capability on is inappropriate.

This candidate instead retains the canonical public purchase_orders, purchase_order_lines and four store allocations, with the current receiving service. It does not install po_ownership, native V4 receiving, quotation processing, email providers, inventory adapters, or a worker login. The existing reviewed V4 authorizer, exact valuation rules, vendor PO-versus-request routing, supply/configuration digests, immutable receipts, reservations, and worksheet seals are reused. The existing configured financial initialization service runs in the same transaction; failure rolls back the whole decision.

Proposed activation, for separate owner approval
1. Review the explicit production_submission_schema.install migration and its database privileges. It is never invoked by web startup or an HTTP endpoint. It requires the bound target, active owner ADMIN, worksheet schema, and a nonempty independent approval reference.
2. It adds the submission ledger/document tables and a versioned immutable production_submission_contract. It keeps the private Alembic worksheet head at p4_0003 and does not import the incompatible isolated writer/receiving stack. The overlay is a distinct qualified profile; future schema upgrades require an explicit compatibility review.
3. Four existing public columns become nullable: vendors.square_vendor_id permits a legitimate internal supplier without inventing a Square identity; the three purchase-order planning parameters permit manual orders without fabricated forecasting values. Existing public records are not rewritten.
4. The NOLOGIN PO-writer role receives the listed SELECT/INSERT and narrow private-ledger UPDATE privileges. It receives no inventory UPDATE, DELETE, provider, or login permission. Only the explicit migration grants membership. Database triggers require an exact owner authorization, conserve approved quantities/valuations/store allocations, serialize supply changes, prevent unreviewed overlapping purchases, and retain original audit facts.
5. Keep PURCHASING_V4_OWNER_INSPECTION_ENABLED=true as the verified workspace binding. Only after approval, migration qualification and release qualification, opt in with PURCHASING_V4_PRODUCTION_SUBMISSION_ENABLED=true. Its code default is false. An absent ledger, owner mismatch, incompatible ownership stack, unqualified role, or missing guards fails closed.
6. PURCHASING_V4_SUBMISSION_PAUSED=true pauses new reviews/authorizations while retaining authenticated receipt/history/document reads and canonical receiving.

Authorization and security implications
The existing session middleware and get_current_principal dependency remain authoritative. Every submission is checked server-side against the configured PURCHASING_OWNER_PRINCIPAL_ID, an active ADMIN role, active employment linkage when present, the exact database target, and the immutable commitment owner. CSRF and the final explicit acknowledgment remain required. The actor is never accepted from request JSON.
This is intentionally the existing configured owner who is an ADMIN; it does not grant every ADMIN, MANAGER, LEAD or STORE user purchasing authority. Other administrators remain denied unless a separate delegation design is approved.
The reviewed UI and bundled assets are byte-for-byte identical to parent 5cc6b748. The new context flags become true only in the approved production submission profile. Preview remains optional and selections, final confirmation, duplicate-click handling and same-command recovery are unchanged.
This path can create real financial obligations after activation. Newly authorized purchasing facts cannot be silently edited or expanded through legacy editors; receiving quantities, status, shipment history and closed-unfulfilled balances continue through the existing service. Canonical legacy operations on unrelated old orders remain available. Vendor routing still distinguishes direct POs from confirmation requests. Recording a confirmation request creates no commitment. Quotation finalization and automatic email are not enabled by this candidate. Manual immutable vendor documents remain available; no mail-delivery command is queued.
