## Integrated application

`app.purchasing_v4.integration_app` composes the existing `app.main` web application with the accepted V4 factories. It uses the existing principal/session/CSRF protections and the same explicitly configured purchasing owner as V3. The owner lands at `/purchasing-v4`; Policies, Purchases, Vendor quotes, Needs Attention, Legacy orders and Release status provide one workspace. Explicitly delegated receiving users land at `/receiving`. Other users retain their original landing routes.

Capabilities default off: workspace, configuration, generation, authorization, receiving, inventory and email. Dependency validation rejects incompatible combinations. The Phase 9 factory requires a loopback disposable PostgreSQL URL, refuses live adapters and blocks external networking. The existing production entrypoint does not import it. There is no production activation environment switch in this phase. CLI switches are isolated qualification controls, not instructions to change Render.

The existing Phase 8 email scheduling middleware and startup work are retained. Remapped routes retain explicit dependency overrides against the existing authenticated principal; retaining only endpoints would lose both authorization and background dispatch behavior. Signed vendor callbacks alone bypass the session-login middleware; exact raw-body signature and timestamp validation remain mandatory. Source refresh on login is disabled in this isolated process so legacy login cannot call production Square.

Legacy order lists in the integrated workspace include only orders with an explicit LEGACY writer. Early service guards reject V4 orders through legacy add, refresh, edit, invoice and delete paths, before external reads or mutations. Database one-writer and immutable financial safeguards remain the final boundary. Existing legacy paths and service defaults are retained when the V4 integration is absent.

## Receiving and commitments

Fixed HWY 99: Receive → Verify Quantities → Store Allocations → Save & Submit. Saved allocations are prefilled and editable by the owner. Save retains only a draft. Save & Submit retains one physical event and durable inventory commands; original ordered quantities, cumulative previous receipts and supplier outstanding balances remain distinct. Unknown provider outcomes require evidence reconciliation against the same operation identity. No separate warehouse, arrival confirmation or dispatch workflow is added.

Original V3 POs retain their writer and receiving path; no historical adoption or receipt replay occurs. V4 reads existing incoming supply through the accepted evidence contract. Existing advisory locks, reservations, review digests, owner command receipts and financial bridges continue to prevent competing commitments and stale authorizations.

Partial inventory runs qualify a returned pair only when the existing retained collector certificate uniquely proves its exact variation/store, run timestamps and observed membership. Caller-specified age, row freshness, location identity and source timestamp constraints still apply. Missing, malformed, duplicate and conflicting certificates remain unknown. An unrelated missing pair does not invalidate an independently proved pair. No hardcoded V3 source-age default is imported.

Availability reconstruction now treats physical counts as barriers for days crossing the count, while allowing later days only when complete movements, sales and a qualified anchor prove their trajectory. Read-only operational status exposes actual refresh and coverage timestamps; reconciliation covers fourteen business domains, all public/private record hashes, foreign keys, PO writers and historical balance exceptions. ## Rollback and forward recovery

Operational rollback first disables new generation/authorization/email and inventory effects as appropriate, while retaining the current compatible schema, original records, in-flight operation IDs, downloads, manual upload and receipt investigation. Email pause is independent of PO authorization and manual handoff. Never restore a backup over unexplained newer external effects.

Already issued V4 POs must retain their V4 receiving/reconciliation capability. Returning the entire application to an old binary is not a complete rollback: it cannot take ownership of V4 orders. Retain the qualified V4 receiver or halt new activity until compatible forward recovery is available. V3 remains writer for its original POs. No schema downgrade, evidence deletion, replay of old receipts or financial reversal is a rollback mechanism.

For cold recovery, initialize a separate PostgreSQL cluster, restore explicit role prerequisites (including mail-worker membership inherited by the outbox login), then schema, records, sequences, owners and grants. Isolated tests use local authentication without copying production passwords. Compare record hashes, schema objects, functions, grants, constraints and original byte hashes before resuming. PostgreSQL 18 reserialization of historical CHECK expressions is compared by independent parse roundtrip, not ignored.

A backup taken while mail is SENDING or Square is IN_FLIGHT may precede provider acceptance. Reconcile against the independent provider using the original retained identity. The tests restore into a newly initialized cluster and show one mail send, one receipt event, unchanged accepted remote adjustments and no new recovery commitments. External effects cannot be undone by restoring SQL.

The local qualification is macOS/PostgreSQL 18.6 and simulated providers. It does not certify live Square, live inbound Resend, production DNS, Linux deployment, remote database ACLs, or external legacy PDF storage. Public record/pointer preservation is verified; those external production originals require a separately qualified backup before cutover. Root Google MX and employee mail must remain unchanged.
